## 2. W1 变更记录迁移（核心）

### 2.1 目标结构

```
CHANGELOG.md          # [Unreleased] + 当前最新版本（永远只有这两段）
changelogs/
  README.md           # 归档说明与索引
  <版本>.md           # 历史版本，一个版本一个文件（发版时由上一版本移入）
```

规则：

- `CHANGELOG.md` 顶部固定 `## [Unreleased]`，分类：`新增 / 改进 / 修复 / 升级注意`；
- 版本段标题：`## [0.4.5] - YYYY-MM-DD`；
- 版本开头可有 `### 亮点`（**不强制**），人话写 2~3 条；
- 不兼容项放 `升级注意`，写清迁移方式；
- 每次发版：新版本段写进 `CHANGELOG.md`，**上一版本整段移入 `changelogs/<版本>.md`**；
- 归档缩略：`CHANGELOG.md` 超过约 2000 行或满一年时，把最旧版本移入归档（自动化留 v1）。

## 3. W2 CI（按渠道分档）

新增 `.github/workflows/ci.yml`，与 AGENTS.md §9 / `docs/dev-flow.md` §6 的渠道规则对齐：

| 作业 | 触发 | 内容 |
|---|---|---|
| `check` | 所有 `pull_request`（→ develop / main）+ push 到 `develop` / `main` | `uv sync --frozen` → ruff check / format --check → mypy（`src/aris/core` + `src/aris/store`）→ `pytest -q`（依赖真库与模型的用例自动 skip） |
| `integration` | `pull_request` 目标为 `main`（正式 / beta 的发版 PR）+ push 到 `main` | 缓存并启动便携 PostgreSQL（`data/pg`，空库每次初始化）+ 缓存 embedding 模型（`data/models`）→ `aris db init/start/migrate` → 全量 `pytest` → `aris serve --dry-run` 冷启动自检 |
| `smoke` | `push` 的 `alpha-v*` tag（只在 develop 打） | `uv sync --frozen --no-default-groups`（不装 embedding 组）→ `aris --version` / `aris info` → `serve --dry-run --skip store.db,knowledge` |

规则与约定：

- **渠道由分支名表达**（2026-11-01 定）：正式版 `release/vX.Y.Z`，beta `release/beta-vX.Y.Z`；
  alpha 不走 release 分支，直接在 `develop` 打 `alpha-vX.Y.Z` tag。workflow 只读事件自带的
  分支 / tag 信息，不需要额外标签或标题约定。
- **beta 与正式版同档**：v0.4.5 不做打包，两者都跑完整测试（真 PG + embedding + 冷启动）；
  打包与 Release 留到 v1 的 CD。
- 所有作业都必须能被 ruleset 当作「必需检查」：被 `if` 跳过的作业 GitHub 视为**通过**，
  不会卡住不相关的 PR；`concurrency` 按 ref 取消上一轮，省额度。
- 作业名（`check` / `integration` / `smoke`）就是 ruleset 里的 checks 上下文，改名要同步
  `.github/rulesets/`。
- **自动合并用原生 auto-merge**（2026-11-01 定）：上游开启 Allow auto-merge，开发者开
  release PR 后执行一次 `gh pr merge --auto --merge`，必需检查全绿后自动合并。
  workflow **不替人合并**，仓库不存 PAT（fork PR 的 token 只读，存长期 PAT 安全面更大）。
- 仓库内提供参考 ruleset：`.github/rulesets/require-ci-main.json`（`main` 要求 `check` +
  `integration`）、`.github/rulesets/require-ci-develop.json`（`develop` 要求 `check`）。
  需要在**上游**导入后生效（fork 的设置不影响上游）。
- 首次真实运行要等开发者推送；fork 发起的首个 PR 可能需要在 Actions 页面手动批准一次。

## 4. W3 发版流程与脚本

### 4.1 定稿流程

日常：

```
feature 分支 → PR → develop（--no-ff 合并）
```

发版（**只有一次 PR**；正式版与 beta 同结构，渠道由分支名表达）：

1. 从最新 `develop` 切 release 分支：`bash scripts/release.sh [--beta] <版本|patch>`（内部调 `bump-version.sh`）；
2. 在该分支封 `CHANGELOG.md` 的版本段；
3. `bash scripts/release-check.sh` 必须 PASS；
4. 提交 `chore(release): v0.4.5 …`；
5. 推送 release 分支到 fork；
6. 上游 PR：`release/v0.4.5 → main`（beta 为 `release/beta-v0.4.5 → main`；首次合并会带出此前差异）；
7. 在 PR 上开启原生自动合并：`gh pr merge --auto --merge`；必需检查（`check` + `integration`）全绿后自动合并；
8. 合并后在上游 `main` 打 tag 并推送：正式版 `v0.4.5`、beta `beta-v0.4.5`；
9. 再开 PR：`main → develop`，标题 `chore: 同步 main 回 develop`，`--no-ff` 合并；
10. 删除 release 分支（本地与远端）；
11. **不创建 GitHub Release**（等 GUI 打包后补）。

alpha 例外：只在 develop 打 `alpha-vX.Y.Z`，不进 main；推送 tag 时 CI 自动跑 `smoke`。

### 4.2 `scripts/release.sh`

一个本地脚本（**不自动推送**），职责：

- 校验：当前在 develop、工作区干净、与 upstream/develop 同步、版本号未占用；
- 切分支（参数给版本或 patch/minor/major）：正式版 `release/vX.Y.Z`，`--beta` 时
  `release/beta-vX.Y.Z`；`--alpha` 直接拒绝（alpha 在 develop 打 tag，不走 release 分支）；
- 调 `bump-version.sh`；
- 提示手工封 `CHANGELOG.md`（不自动改内容，避免生成没人味的文字）；
- 跑 `release-check.sh`；
- 打印后续命令：提交、推送、PR、`gh pr merge --auto --merge`、tag、回合并。

| 上游与 fork 分支分叉 | 所有发布合并与 tag 只在上游；fork 只做 `--ff-only` 跟随 |
| tag 同名不同提交 | 上游 tag 为唯一来源；fork 旧 tag 删除 |
| CHANGELOG 合并冲突 | 只在 release 分支封版；`[Unreleased]` 在 develop 累积时保持顶部 |
| CI 依赖真库失败 | `check` 里继续 skip；真库 / 模型只放在发版 PR 的 `integration`，失败时看 `data/pg` 缓存与模型下载 |
| 发版流程首次跑不顺 | 严格按 §4.1 顺序；每步确认后再下一步 |
| 上游未开 auto-merge / 未导入 ruleset | 开 PR 前先核对仓库 Settings；没开就退化为手动合并，不影响测试结果 |
| fork PR 首跑需要批准 | 上游 Actions 页面手动批准一次，之后同仓库 PR 正常 |

## 10. 交接说明（给执行 agent）

- **开工前**：读 `AGENTS.md` → 本文件（尤其 §0.1 当前状态）→ `docs/dev-flow.md`；用 §0.1 的命令复核仓库状态；
- **不执行 `git push`**，所有推送由开发者做；
- **不执行 `bump-version.sh`**，不改 `__version__`；
- **不创建 GitHub Release / tag**；
- 顺序：W1（changelog 迁移）→ W2（CI）→ W3（release 脚本 + 文档）→ W4/§5.1（文档同步与 `docs/archive` 指针清理）→ `bash scripts/check.sh` → 提交；
- 完成后把改动文件清单与 check.sh 结果交给 Lead 复核。

## 11. 执行顺序

1. 前置清理提交；
2. W1 changelog 迁移 + release-check；
3. W2 CI；
4. W3 release 脚本 + 流程文档；
5. W4 文档同步（含 §5.1 `docs/archive` 指针清理，可并行外包给另一个 agent）；
6. `scripts/check.sh` → 提交 → 合并 develop；
7. 按 §4.1 发 `v0.4.5`。
